# NetSifr platform — real implementation plan (v2: social learning & action platform)

## Context

This started as a request to turn a Claude Design prototype (`project/NetSifr LMS Prototype v2.dc.html` + chat transcript in this otherwise-empty repo) into a real Next.js app with a full backend. The first pass of this plan modeled the product as a single-purpose LMS (`Program` = course cohort) with email/password auth, a flat Admin/Participant role, and a `User.organizationId` single-tenant-shaped schema.

The user reviewed that plan and substantially corrected and expanded it, based on where NetSifr actually wants to go: **an LMS is the first module of a broader social learning and action platform** — courses, but also events, volunteer calls, and action projects, all discoverable in one place, with people building a cross-cutting record of learning and impact and connecting with each other around it. They also caught several real architectural mistakes in the first pass (tenancy model, invite security, immutability of graded content, attendance-proxy honesty, stale-JWT authorization, missing audit/lifecycle/production concerns) and want native iOS/Android apps down the line, website first.

This plan supersedes the first version entirely. It keeps what was validated against the prototype's actual logic (points/persona/attendance formulas, quiz retake rule, invite lifecycle shape) but rebuilds the data model and roadmap around the corrected identity/tenancy design and the `Initiative → Opportunity → {Course, Event, Volunteering, ActionProject}` structure, so that Phase 1 (the LMS) is built on foundations that don't have to be re-cut when Events/Volunteering/Community/Recognition land later.

**Scope discipline**: only Phase 1 (learning) is being built now. Everything else (Events, Volunteering, Community, Action Projects, Recognition-as-a-ledger) is real schema/architecture the plan accounts for so Phase 1 doesn't paint the product into a corner — it is **not** all being coded in this pass. Native mobile apps are explicitly future work; the only thing this plan commits to *now* for mobile's sake is keeping business logic in framework-agnostic modules so a future API layer can wrap them without a rewrite.

## Corrected foundations (apply throughout, not just to the learning module)

**Identity & tenancy.** `User` is a global person-level identity (not scoped to one organization). `Credential { type: EMAIL_PASSWORD | PHONE_OTP, identifier, secretHash, verifiedAt }` is unique on `(type, identifier)` **globally** (not per-org) — since a person can belong to multiple organizations, tying login identity to one org would break the moment someone joins a second one, and it removes the "which org is this email in" ambiguity at login for free. Org-level access is `OrganizationMembership { userId, organizationId, role: OWNER|ADMIN|COORDINATOR|MEMBER, status: ACTIVE|SUSPENDED|LEFT }` — every person who has any relationship to an org (participant, volunteer, staff) gets a `MEMBER`-or-above row; elevated roles are for staff. Resource-scoped roles (facilitator on one cohort, coordinator on one volunteer call) live in their own membership tables (`CohortStaffMembership`, `EventStaffMembership`, `ProjectMembership`, `VolunteerCoordinatorMembership`), never folded into the org-wide role. **Sensitive actions re-fetch current membership/status from the database inside the Server Action itself** — the JWT session only identifies *who* the user is, never their current role/status, so a revoked admin or suspended member is cut off immediately rather than "whenever their token happens to expire."

**Account lifecycle.** `User.status: ACTIVE|SUSPENDED` and `OrganizationMembership.status: ACTIVE|SUSPENDED|LEFT` exist from day one — there is no v1 that ships without a way to disable an account.

**Product catalogue shape.** `Initiative` is an umbrella campaign (e.g. "Karachi Climate Resilience Initiative 2027") that can group any mix of activities. `Opportunity` is the common discoverable envelope every activity type shares — `{ id, organizationId, initiativeId?, type: COURSE|EVENT|VOLUNTEERING|ACTION_PROJECT, title, slug, summary, coverMediaId, visibility, status, applicationOpensAt/ClosesAt, startsAt/endsAt, capacity?, locationMode: ONLINE|PHYSICAL|HYBRID, locationId?, ownerUserId }` — this is what powers one `/discover` feed and one recommendation surface, without forcing every activity into the same operational state machine underneath. `OpportunityOrganization { opportunityId, organizationId, role: OWNER|CO_HOST|PARTNER|SPONSOR }` lets a workshop be "hosted by NetSifr and Pakistan Red Crescent, with academic support from SSUET" — only the owning org controls it by default, partner access is explicit. Each type then owns its own tables and state machine (only `COURSE` is built now; the others are named/reserved, not modeled in full):
- `COURSE` → `Course` (reusable identity/description) → `CourseVersion` (immutable curriculum snapshot — see below) → `Cohort` (one scheduled delivery, replaces the old flat "Program") → `Enrolment`. **The `Opportunity` row is 1:1 with the joinable instance, not the reusable identity** — for courses that's the `Cohort` (mirrors `Event`↔`EventOccurrence` and `VolunteerOpportunity`↔`Shift`: the reusable thing is authored once, discovery/joining happens at the scheduled-instance level). This is also what makes `OpportunityOrganization` co-hosting correct per-delivery — NetSifr could author a `Course` once and run one cohort solo, another co-hosted with a partner, without the `Course`/`CourseVersion` themselves knowing anything about hosts.
- `EVENT` → `Event`, `EventOccurrence`, `EventRegistration`, `EventCheckIn`, `EventFeedback` (Phase 2, reserved names only for now).
- `VOLUNTEERING` → `VolunteerOpportunity`, `VolunteerApplication`, `VolunteerShift`, `ShiftSignup`, `ServiceLog`, `ServiceVerification` (Phase 3, reserved only).
- `ACTION_PROJECT` → `ActionProject`, `Team`, `ProjectMembership`, `Task`, `Contribution` (Phase 5, reserved only).

**Discover, and its tension with invite-only enrolment.** Your Person→Discover→{Learn, Attend Events, Volunteer, Join Action Projects}→Community & Recognition diagram confirms the shape above and is worth naming as an actual route (`/discover`) rather than leaving implicit — one hub, one recommendation surface, all four activity types feeding the same downstream Community & Recognition layer. But it also surfaces a real tension with the original NetSifr prototype's model, which was explicitly **invite-only** ("Programs are invite-only. Your facilitator sends a link... it lands here"): a public browse-and-apply `/discover` implies self-service applications (which fits `VolunteerApplication`'s `APPLIED` status naturally), while Phase 1's courses are still invite-gated. Default for Phase 1 (flagged, not silently assumed): keep enrolment invite-only exactly as decided, and treat `/discover` itself as a Phase 2+ concept — it earns its keep once there's more than one `Opportunity` type worth browsing and volunteering's self-serve `APPLIED` flow exists. Phase 1's participant home is still the simpler "Your Programs" picker (invited/active/completed), not a public catalogue. Revisit this default once Phase 2/3 are actually being scoped.

**Course/Cohort/immutability.** `Course` is the reusable curriculum identity. `CourseVersion` is an **immutable** snapshot of weeks/modules/quiz questions+correct answers/deadlines — once any `Cohort` running that version has any enrolment activity (an attempt, a submission, an attendance record), that version is frozen; editing content creates a new `CourseVersion` rather than rewriting history, and a live cohort can only move to a newer version through an explicit "publish new version to this cohort" action. `Cohort` (`{ courseVersionId, cohortLabel, startsAt, attendanceUnlockMinutes, status: DRAFT|LIVE|ARCHIVED }`) is the scheduled delivery — this is what `Enrolment`, deadlines, staff, and attendance actually attach to, not the reusable `Course`. Its own calendar (per-week dates) lives in `CohortSession`, not on `Cohort` or `Week` directly — see "Week scheduling" below. `CohortStaffMembership { userId, cohortId, role: FACILITATOR }` replaces the old `ProgramMembership` — same "schema now, functional later" status as before (v1 authority is still `OrganizationMembership.role IN (ADMIN, OWNER)`; this table exists but is unused for authorization until the facilitator fast-follow).

**Week scheduling — corrected by your diagram.** The first pass put `startsOn`/`endsOn` directly on `Week`, which is wrong once `Week` lives under the immutable `CourseVersion`: two different cohorts running the same `CourseVersion` need different calendar dates for "week 3," so a concrete date can't live on the shared curriculum row. Splitting it in two, matching your Course→CourseVersion diagram exactly: `Week { id, courseVersionId, orderIndex, title }` stays pure curriculum structure (immutable with its `CourseVersion`, no dates). `CohortSession { id, cohortId, weekId, startsOn, endsOn }` is the per-cohort calendar instantiation — one row per week, auto-created when a `Cohort` is created from a `CourseVersion`, dates auto-filled as `cohort.startsAt + 7*orderIndex` *at creation time only*, then independently editable per session so a holiday or an irregular cadence in *this* cohort doesn't touch the shared curriculum or any other cohort. Anything date-driven (the Home dashboard's "current week," the attendance-% denominator, "this week's recording") reads `CohortSession`, not `Week`. Treat `startsOn`/`endsOn` as calendar dates (no time component) under an explicit organization timezone (`Organization.timezone`, IANA name) — all other timestamps (`createdAt`, `submittedAt`, etc.) stay UTC instants.

**Invitation, corrected.** `Invitation` (renamed from `Invite`) is fully separate from `Enrolment` — `Enrolment` is created **only** on acceptance, never `INVITED`/`DECLINED` states on it (those were wrongly modeled on `Enrolment` in the first pass; removed). `Invitation { id, cohortId, normalizedEmail, tokenHash (never plaintext, matching PasswordResetToken's own pattern), status: PENDING|ACCEPTED|DECLINED|EXPIRED|REVOKED, expiresAt, acceptedByUserId?, createdByUserId }`. Acceptance requires the signed-in user's **verified** email to match `normalizedEmail` — this is what stops a forwarded invite link being accepted by the wrong account. `declineInvite` sets `Invitation.status = DECLINED` (no `Enrolment` ever existed to decline).

**Module content immutability enforcement.** `Module{type}` + 1:1 side tables from the first pass stands, but "exactly one matching side-table row per Module" is enforced **transactionally** in the `upsertModule` action (create/replace both rows in one transaction; a periodic integrity check query is cheap insurance, not a substitute) rather than assumed from the type column alone. Quiz attempts and assignment submissions reference their `CourseVersion`-scoped module directly, which is itself frozen once live — this is what gives "immutable published content" for free instead of needing a separate content-snapshot copy per attempt.

**Attendance renamed to what it actually measures.** Since Google Drive gives no supported playback API, the schema and UI copy should never claim to know the video played — rename the old `AttendanceRecord.watchedSeconds/attendedAt` to `engagedSeconds`, `engagementThresholdReachedAt`, `attendanceConfirmedAt`, `attendanceConfirmationMethod: ENGAGEMENT_PROXY|ADMIN_OVERRIDE|LIVE_ATTENDANCE` (the last value reserved for when the Events module's `EventCheckIn` covers an in-person/live session). Add `PlaybackSession { id, userId, recordingModuleId, nonce, startedAt, lastHeartbeatAt }` with a partial-unique constraint enforcing **one active session per (user, recordingModuleId)** — the heartbeat endpoint validates the nonce belongs to the caller's current session before accepting a delta, which stops the multi-tab/replay races the old bare "ping" design was exposed to. Participant-facing copy should say "recording page open ≥ N minutes," never "watched" — this is an engagement threshold, not proof of viewing, and should be described that way in the UI, especially since this becomes load-bearing later if NetSifr ever needs accredited/certified hours (at which point Drive should be replaced with a real playback-API video vendor for that specific course — flagged, not solved, here).

**Recognition, corrected.** Do not keep expanding one hardcoded points formula as more activity types arrive. Add `ContributionEvent { id, userId, organizationId, type, sourceType, sourceId, occurredAt, verificationStatus, verifiedByUserId?, pointsPolicyVersion?, idempotencyKey }` as an **immutable ledger** — attendance-confirmed, quiz-submitted, assignment-graded, (later) event-attended / verified-volunteer-hours / project-led all write one `ContributionEvent` row each. The learning module's own tables (`Enrolment`, `Submission`, `Grade`, etc.) stay the source of truth for what happened; `ContributionEvent` is what points/badges/certificates/leaderboards/impact-reports read from, so adding Events/Volunteering later means writing new `ContributionEvent` rows, not touching the points formula. Phase 1 still computes the same points formula as before (attendance/read/quiz/assignment-derived) — it just does so by **writing** `ContributionEvent` rows at the moment each thing happens (transactionally alongside the source write, keyed by an idempotency key so retries can't double-count) rather than only computing on read. Reading total points is a `SUM` over `ContributionEvent` for that user (± program filter), which is simpler than the original "recompute from 4 different tables" approach and is the one that survives Phase 2+.

**Taxonomy.** The flat `Interest` lookup becomes `Topic`/`Cause`/`Skill`/`Location` + join tables (`UserInterest`→`UserTopic`, `UserSkill`, `OpportunityTopic`, `OpportunitySkillRequirement`, `OrganizationFocusArea`) — this is what later powers "you're into climate justice and live in Karachi, ten volunteers needed for risk mapping." Phase 1 only needs `Topic` + `UserTopic` (renamed from `Interest`/`UserInterest`, same shape) populated; the rest are reserved names for Phase 3+.

**Community/social layer** (`Community`, `CommunityMembership`, `Post`, `Comment`, `Reaction`, `Follow`, `Report`, `ModerationAction`, `Notification`, `NotificationPreference`) is Phase 4 — not built now, but every `Post` will need an explicit `audience: PUBLIC|ORGANIZATION|COMMUNITY|COHORT|PROJECT_TEAM|PRIVATE` from day one of that phase so cohort discussions or volunteer details can't accidentally leak public — noted now so nobody defaults it to PUBLIC later under deadline pressure.

**Cross-cutting infra, added now rather than bolted on later:**
- `AuditEvent { id, organizationId, actorUserId, action, targetType, targetId, metadata, createdAt }` — every admin override, grade, publish/archive, and role change writes one row. Built alongside the Phase 1 admin actions, not after.
- `MediaAsset` (profile images, event covers, future submission attachments) and `Location` (physical/online/hybrid) — reserved tables created in Phase 1's migrations even though Phase 1 barely uses them, so Phase 2/3 don't need a schema migration just to attach a cover image.
- An outbox/domain-event mechanism (`OutboxEvent { id, type, payload, processedAt }` + a poller, or a hosted queue if the deployment target has one) for notifications and `ContributionEvent` fan-out — even a simple polling worker beats firing side effects inline inside request handlers, which is what tends to quietly drop emails under load.

## Technical corrections from the first pass

- **Next.js 16**, not 15 — confirmed current stable as of Sept 2026 (16.3.x). `middleware.ts` is renamed to `proxy.ts` (exported function renamed `proxy`) in Next.js 16; the plan's route guarding now uses `proxy.ts`. [Next.js 16](https://nextjs.org/blog/next-16), [Renaming Middleware to Proxy](https://nextjs.org/docs/messages/middleware-to-proxy)
- **Auth.js route handler exports both methods**: `export const { GET, POST } = handlers` in `app/api/auth/[...nextauth]/route.ts` — the first pass wrongly described this as POST-only.
- **Password hashing**: Argon2id (not left unspecified) via a maintained Node binding, with NIST-reasonable cost parameters tuned to the deployment's actual hardware at setup time, not copy-pasted defaults.
- **Auth.js Credentials caveat, stated explicitly**: Auth.js does not persist Credentials-provider users itself — this app owns `Credential` storage, hashing, verification, and recovery end to end (which the schema already assumed, but the plan now says so directly rather than leaving it implicit), including login throttling and required email verification before an account can accept invitations or reset a password.
- **Rate limiting**: login, password-reset request, invitation generation, and the engagement-ping endpoint all get explicit per-identifier and per-IP limits — these are the four endpoints an unauthenticated or low-trust actor can hit repeatedly.
- **Production email behavior**: password-reset and invitation links are **never** console-logged outside local development — a missing/misconfigured provider in production must hard-fail the action (visible error, nothing silently degrading to a log line) rather than leak a live credential-bearing link into server logs.
- **CSV export**: sanitize every exported cell against formula injection (prefix a leading `=`, `+`, `-`, `@` with a `'` or otherwise neutralize) since this file opens directly in Excel/Sheets for admins.
- **CSP**: restrict embeds to the Drive origin(s) actually used, no wildcard frame-src.
- **First-admin bootstrap**: a documented one-time seed/CLI step to create the first `OWNER` membership on a fresh database — there is otherwise no way to create the first admin through the UI.
- **Timezone/date semantics**: see "Week scheduling" above — `Organization.timezone` + explicit date fields for anything calendar-shaped, UTC instants for everything else.
- **Testing matrix, per phase, not just "some unit tests"**: typecheck + lint, unit tests, DB integration tests, tenant-isolation/authorization tests (a Suspended/Left member or a member of a *different* org must be provably denied, not just "not tested"), production build, `prisma migrate deploy` against a clean database (never `migrate dev` outside local development — `deploy` is the one that matches how production actually applies migrations), and at least one Playwright end-to-end flow per phase.

## Mobile readiness (web first, native apps later — explicitly deferred, not designed in detail now)

Server Actions are a Next.js/React-only calling convention — a native iOS/Android app cannot invoke them. The one decision that matters *now*, before Phase 1 code exists, so it isn't a rewrite later: **business logic lives in plain framework-agnostic module functions** (`modules/identity`, `modules/organizations`, `modules/learning`, `modules/recognition`, etc. — mirroring the domains above), and both the web app's Server Actions *and* a future versioned JSON API (`/api/v1/...`) are thin callers into those same functions. Phase 1 only builds the Server Action callers (web-only, matches "website first"); the module-boundary discipline is what makes adding `/api/v1` for a native app later an additive project, not a refactor of business rules scattered across page components. No native app work is scheduled in this plan — call it out explicitly as future scope once the web product is live.

## Revised roadmap

**Phase 1 — Learning module (this is "the LMS")**
Identity/tenancy foundation (`User`, `Credential`, `Organization`, `OrganizationMembership`, audit/lifecycle fields), `Topic`/`UserTopic`, `Initiative`/`Opportunity` envelope (created but only ever populated with `type=COURSE` rows), `Course`/`CourseVersion`/`Cohort`/`CohortSession`/`Enrolment`/`CohortStaffMembership`, `Module` family with immutable-once-live `CourseVersion`s, `Invitation` (corrected model), engagement-proxy attendance + `PlaybackSession`, quiz/assignment/grading, `ContributionEvent` ledger + points derivation, admin Builder/Attendance/Submissions/Invites + CSV export, participant onboarding/picker/in-cohort experience. `AuditEvent`, `MediaAsset`, `Location`, and the outbox mechanism are stood up here even though usage is light, so later phases don't start with a migration.
Full per-phase testing matrix (above) applies starting here — this phase also stands up the CI pipeline itself (typecheck/lint/unit/integration/tenant-isolation/build/migrate-deploy/Playwright), since none of it exists yet in this repo.

**Phase 2 — Events (built)**: `Event`/`EventOccurrence`/`EventRegistration`/`EventCheckIn`/`EventFeedback`, capacity/waitlists (auto-promotion on cancellation), one shared QR code per occurrence (`AttendanceConfirmationMethod.LIVE_ATTENDANCE`, 30min-before to 2h-after window) plus admin manual check-in (`ADMIN_OVERRIDE`), feedback gated on check-in, `EVENT_ATTENDED` `ContributionEvent` (150pts), reuses `Location`/`MediaAsset`/`Opportunity` from Phase 1. Events are **self-service** (`Opportunity.visibility = PUBLIC`) — the first activity type `/discover` actually earns its keep on, unlike Courses which stay invite-only. Certificates stay deferred to Phase 6 as originally decided; a course's physical workshop rides on this instead of a second attendance system.

**Phase 3 — Volunteering (built)**: `VolunteerOpportunity`/`VolunteerApplication`/`VolunteerShift`/`ShiftSignup`/`ServiceLog`/`ServiceVerification`, the full status lifecycle (`DRAFT→OPEN→APPLIED→SHORTLISTED→ACCEPTED/REJECTED/WITHDRAWN→CONFIRMED→ATTENDED/NO_SHOW→COMPLETED`), `Skill`/`UserSkill`/`OpportunitySkillRequirement` taxonomy expansion. Self-service like Events; admin console for authoring/applications/hour-verification; participant discover→apply→shift-signup→log-hours→see-verification; `VOLUNTEER_HOURS_VERIFIED` points on verify. See the Phase 3 decisions note below for how that one long lifecycle string is split across the tables.

**Phase 4 — Community & social learning**: `Community`/`Post`/`Comment`/`Reaction`/`Follow`/`Notification`/moderation, audience-scoped from day one (see above).

**Phase 5 — Action projects**: `ActionProject`/`Team`/`ProjectMembership`/`Task`/`Contribution`.

**Phase 6 — Recognition & recommendations**: certificates, skills portfolios, a recommendation engine over `Topic`/`Cause`/`Skill`/`Location`, org/initiative impact dashboards reading the `ContributionEvent` ledger accumulated since Phase 1.

## Product decisions the user asked me to default (flagged as changeable, not hidden assumptions)

- **Cohort completion**: automatic once `endsAt` passes, with an explicit admin "mark complete" override for early completion and a "reopen" action if needed.
- **Progress/attendance-% denominator**: only modules/weeks **released so far** (published, `startsOn <= today`), matching the prototype's own `currentWeek+1` denominator — future content never penalizes current standing.
- **Quiz average**: best attempt (of the allowed 2), not first or latest — all attempts still stored for audit.
- **Enrolment lifecycle**: add `WITHDRAWN` (admin-settable) alongside `ACTIVE/COMPLETED/DECLINED`, reinstatable back to `ACTIVE`.
- **Archived cohorts**: remain viewable read-only (content + history); no new submissions/attendance accepted.
- **Duplicate cohort**: copies the week/schedule structure referencing the same `CourseVersion`; never copies roster, enrolments, attendance, or submissions.
- **Editing published modules**: never in place once a cohort using that version has activity — publish a new `CourseVersion` instead (see immutability above).
- **Cohort roster visibility (participant-facing "This cohort" screen)**: name, persona, avatar, city — never email (email stays admin-roster-only, matching the prototype's own admin-vs-participant field split).
- **Certificates**: not in Phase 1; the `ContributionEvent` ledger and reserved Recognition-module tables make it a Phase 6 addition, not a schema change.
- **Live/physical sessions**: not in Phase 1 — Phase 1 is recorded/self-paced only; in-person attendance rides on Phase 2's `EventCheckIn`.
- **Content release**: manual publish/unpublish per module (matches the prototype exactly), plus a nullable `releaseAt` on `Module` now (cheap to add, enables scheduled release later without a migration) — not acted on by any code until a phase actually needs it.

## Verification

Per-phase gate (all of these, every phase, starting at Phase 1): typecheck + lint clean; unit tests pass (points/streak/persona-vote/quiz-scoring logic get the heaviest coverage — these are the "silently wrong" surfaces); DB integration tests against a real Postgres; tenant-isolation tests proving a different-org member, a Suspended member, and an unenrolled user are all denied where expected; production build succeeds; `prisma migrate deploy` applies cleanly to a fresh database; at least one Playwright flow exercises the phase's headline path end-to-end (for Phase 1: sign up → onboarding → admin creates+publishes a cohort → invites the participant → participant accepts → engages recording past threshold → marks attended → takes quiz → submits assignment → admin grades it → participant sees feedback → admin exports CSV; for Phase 2: admin creates an event+occurrence and publishes it → participant discovers it → registers → self-checks-in via the QR token URL → leaves feedback → admin sees the registration and feedback; for Phase 3: admin opens a volunteer opportunity with a shift → participant discovers and applies → admin accepts → participant signs up for the shift and logs hours → admin verifies the hours → points award and the log reads VERIFIED).

## Phase 3 decisions (Volunteering) — defaulted, flagged (same practice as Phases 1–2)

Built autonomously; these are the judgment calls made along the way, called out for review.

- **Self-service, like Events.** A `VolunteerOpportunity` is 1:1 with a `PUBLIC` `Opportunity` envelope (`type = VOLUNTEERING`) — discoverable on `/discover`, applied to directly. Courses stay invite-only; Events and Volunteering are the self-service types.
- **The joinable unit is the opportunity, not the shift.** Unlike Events (where the `Opportunity` envelope is per-occurrence because you register for a specific occurrence), volunteers **apply to the opportunity**, and `VolunteerShift`s are optional scheduling sub-slots that *accepted* volunteers then sign up for. So the envelope is 1:1 with `VolunteerOpportunity`, and shifts hang off it — this is the shape that matches "apply once, then pick slots," and keeps the `/discover` card at the opportunity level.
- **How the one long lifecycle string maps to tables.** `DRAFT→OPEN→CLOSED/ARCHIVED` is the **opportunity** status (open for applications or not). `APPLIED→SHORTLISTED→ACCEPTED/REJECTED/WITHDRAWN` is the **`VolunteerApplication`** status. `SIGNED_UP→CONFIRMED→ATTENDED/NO_SHOW/CANCELLED` is the **`ShiftSignup`** status. `COMPLETED` is represented by a verified `ServiceLog` rather than a status flag. No single table carries the whole string — it was always three lifecycles superimposed.
- **Service logging + verification mirrors assignment submission + grading.** A volunteer files a `ServiceLog` (hours + date + optional note, optionally tied to a shift); an admin creates a `ServiceVerification` (`VERIFIED`/`REJECTED` + note), exactly like `Submission`→`Grade`. Points are awarded only on `VERIFIED`, written once to the `ContributionEvent` ledger keyed by the log id.
- **Points**: `VOLUNTEER_HOURS_VERIFIED` = **20 points per verified hour** (rounded), tunable via `pointsPolicyVersion` like every other award. Between a reading (40) and a full quiz (150) for a typical 2–4h shift — in scale with the existing economy. Not cohort-scoped (`cohortId` null on the ledger row), same as event attendance.
- **Skills are advisory in Phase 3.** `Skill`/`UserSkill`/`OpportunitySkillRequirement` tables are populated (an opportunity can list required skills, a user can list theirs, and the detail page shows a match), but nothing *gates* application on a skill match — matching-as-a-hard-filter is a Phase 6 recommendation-engine concern. The tables exist now so that's additive later.
- **Capacity/waitlist on shifts**: a `VolunteerShift.capacity` (nullable = unlimited); signup past capacity is refused with a clear message rather than waitlisted (volunteering shifts are smaller and coordinator-managed, unlike open-registration events — a refused signup prompts the volunteer to pick another slot). Revisit if real usage wants waitlists here too.
- **Only ACCEPTED applicants can sign up for shifts or log hours** — the application gate is the trust boundary, mirroring how enrolment gates course content.

## Phase 2 review — findings & tenant-safety hardening

After Phase 2 shipped, the codebase got an independent review pass (fresh eyes, not trusting the build-time summary). The architecture held up well — the `CourseVersion` immutability lock, the `ContributionEvent` idempotency-keyed ledger, the hash-only `Invitation` with verified-email-match acceptance, and the `SELECT … FOR UPDATE` waitlist promotion are all correct and were kept. The review surfaced one systemic gap and a few smaller items, being addressed in a dedicated hardening pass **before Phase 3** (so Volunteering is built on the corrected pattern rather than inheriting the gap):

- **Authorization checked the gate, not the resource (systemic — being fixed).** Admin actions gated via `requireAdminContext` → `assertOrgAdmin(userId, getDefaultOrganization().id)`, which proves *"you administer the one org"* but never *"the cohort/occurrence you're mutating belongs to that org."* The module mutations (`updateCohortStatus`, `duplicateProgram`, `addWeek`, `reorderWeeks`, `upsertModule`, `gradeSubmission`, `overrideAttendance`, `generateInvitation`, `createOccurrence`, `updateOccurrenceStatus`, `adminCheckIn`) and the admin reads that return PII (`getCohortRoster`, `getSubmissionsForCohort`, `getOccurrenceDetail`, `getRegistrationsForOccurrence`, `getFeedbackForOccurrence`) took a bare ID with no `organizationId` scoping. Safe today *only* because `getDefaultOrganization` guarantees a single org — but the earlier claim that a second org is "a data change, not a rewrite" understated it: the data is org-scoped, the *access control was not*. Fix: an `assertInOrg` helper in the organizations module, threaded through every admin mutation and cross-tenant read (org verified inside the module, so a future `/api/v1` caller is protected too, not just the Server Action edge). This makes the module boundary the security boundary, consistent with the mobile-readiness rationale.
